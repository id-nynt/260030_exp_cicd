# Manual execution guide

This guide explains the framework as it is currently implemented. It separates the deterministic mock validation from the real GitHub/telemetry demonstration.

## Why the MAS console appears

The real MAS console is started by the Gradle `runReal` task, which executes
`java-jason/real.mas2j`:

```text
gradle runReal --console=plain --no-daemon
```

That task starts a local multi-agent system in the foreground. Its console
output is the BDI execution stream: selected actions, observations converted to
beliefs, plan messages, and terminal state. It is not a second CI/CD pipeline
and it is not the GitHub Actions console.

The `BDI MAS CONSOLE` window is the Gradle process running `real.mas2j`. Stop
it with `Ctrl+C` when running it manually. The deterministic scenario runner
stops its MAS automatically after the expected terminal action.

## The three-window layout

Run the real demo from one launcher shell. It opens three clearly titled
PowerShell windows and, optionally, a browser:

| Window | Run/watch | Evidence |
|---|---|---|
| `TELEMETRY MONITOR` | `/health`/`/metrics` for staging and production | service status, latency, error rate, health |
| `BDI DECISION MONITOR` | structured JSONL event file | goals, percepts, beliefs, decisions, GitHub IDs |
| `BDI MAS CONSOLE` | Jason launcher | raw Jason plans, `run_job`, retries, recovery, terminal state |
| Browser — optional | `http://localhost:8081/metrics` and `http://localhost:8082/metrics` | raw Prometheus-format telemetry |
| Browser — optional | application URLs and `/metrics` | deployed UI and raw metrics |
| GitHub browser — real mode | Actions run page | remote workflow jobs and their step logs |

For a machine-readable BDI stream in real mode, watch:

```powershell
Get-Content .\java-jason\runtime-artifacts\healthy-001.jsonl -Wait
```

Important real-mode events are `bdi_decision`, `github_dispatch_accepted`, `github_execution_started`, `observation_normalized`, `percept_published`, and `execution_terminal`.

## 1. Edit the project configuration

Edit these two source files only:

```text
01_pipeline.yaml   executable jobs, dependencies, recovery trigger, retry policy
02_goal.yaml       achievement, maintenance, and avoidance goals
```

Do not manually edit `03_workflow_model.yaml`, `bdi_project.asl`, or the generated section of `bdi_agent.asl`. They are derived artifacts.

## 2. Validate and generate the model

From the repository root:

```powershell
py .\tools\model_transform.py
```

The deterministic transformation is:

```text
01_pipeline.yaml + 02_goal.yaml
  -> 03_workflow_model.yaml
  -> bdi_project.asl
  -> bdi_agent.asl = bdi_project.asl + bdi_generic.asl
```

The command fails on unknown entities, unknown dependencies, cycles, malformed comparisons, unsupported observables, invalid recovery targets, or invalid retry values. Review the generated diff before executing anything:

```powershell
git diff -- 03_workflow_model.yaml bdi_project.asl bdi_agent.asl
```

## 3. Run deterministic tests first

Run transformation tests:

```powershell
py .\tools\test_model_transform.py
```

Run the complete deterministic BDI validation:

```powershell
powershell -ExecutionPolicy Bypass -File .\java-jason\run_scenarios.ps1
```

The scenario runner does not contact GitHub, Docker, or OpenTelemetry. It uses in-memory execution and observation providers and writes:

```text
java-jason/scenario-artifacts/scenario1.json ... scenario8.json
java-jason/scenario-artifacts/phase3-summary.json
java-jason/scenario-artifacts/scenario1.log ... scenario8.log
```

It automatically checks action order, retries, recovery, forbidden downstream actions, terminal state, goal result, and required belief changes. This is the fastest way to verify BDI reasoning before a real GitHub run.

## 4. Start local staging and production telemetry

For the local application/telemetry window:

```powershell
docker compose up -d --build
Invoke-RestMethod http://localhost:8081/health
Invoke-RestMethod http://localhost:8082/health
```

Then open `http://localhost:8081/metrics` and `http://localhost:8082/metrics`. The application exposes Prometheus-format metrics generated by its OpenTelemetry instrumentation. The repository does not run a separate OpenTelemetry Collector or Grafana server; Java polls the configured endpoints directly.

## 5. Configure and start the real MAS

The real MAS requires a GitHub token, repository, branch, and reachable telemetry endpoints:

```powershell
$env:GITHUB_TOKEN = '<token with Actions read/write access>'
$env:GITHUB_REPOSITORY = 'OWNER/REPOSITORY'
$env:GITHUB_REF = 'main'
$env:BDI_EXPERIMENT_ID = 'healthy-001'
$env:BDI_RELEASE_ID = 'candidate-001'
$env:STAGING_HEALTH_URL = 'http://localhost:8081/health'
$env:STAGING_METRICS_URL = 'http://localhost:8081/metrics'
$env:PRODUCTION_HEALTH_URL = 'http://localhost:8082/health'
$env:PRODUCTION_METRICS_URL = 'http://localhost:8082/metrics'
$env:BDI_LOG_FILE = 'java-jason/runtime-artifacts/healthy-001.jsonl'
```

The `entity-execution.yml` workflow must already exist on the selected GitHub branch. Start the foreground MAS in Window B:

```powershell
powershell -ExecutionPolicy Bypass -File .\java-jason\run_healthy_demo.ps1
```

Expected control flow:

```text
Jason run_job(build)
  -> GitHub workflow_dispatch(entity=build)
  -> poll the exact GitHub run
  -> execution_status and duration observations
  -> Jason status(build,success)
  -> Jason selects run_job(test)
  -> ...
```

Use Window A for local telemetry and the GitHub Actions web page for remote job logs. The MAS console is the BDI window; it will not display the full GitHub shell-step log.

## 6. Inject an error in a controlled real run

The real executor accepts a properties file through `BDI_EXECUTION_PLAN`. Create `experiments/manual-failure.properties`:

```properties
build.1.failure_mode=none
test.1.failure_mode=test_failure
test.2.failure_mode=none
security.1.failure_mode=none
staging.1.failure_mode=none
production.1.failure_mode=none
```

Then set:

```powershell
$env:BDI_EXECUTION_PLAN = (Resolve-Path .\experiments\manual-failure.properties)
$env:BDI_EXPERIMENT_ID = 'test-retry-001'
$env:BDI_LOG_FILE = 'java-jason/runtime-artifacts/test-retry-001.jsonl'
powershell -ExecutionPolicy Bypass -File .\java-jason\run_healthy_demo.ps1
```

Expected BDI sequence:

```text
build -> test -> test -> security -> staging -> production
```

Compare: (1) GitHub Actions, where the first `test` run fails and the second succeeds; (2) the MAS console, where `run_job(test)` appears twice with failure then success beliefs; and (3) the JSON-lines log, where decisions, terminal observations, normalized percepts, and subsequent decisions share correlation metadata.

For a production failure and recovery, configure two failing production attempts. The generated model maps production recovery to `rollback_production`; BDI selects it and executes it through the same `run_job(Recovery)` action.

## 7. Stop and understand generated files

Stop the foreground MAS with `Ctrl+C`, then stop local services:

```powershell
docker compose down
```

The generator updates `03_workflow_model.yaml`, `bdi_project.asl`, and `bdi_agent.asl`; Java compilation updates `java-jason/build`; scenario execution updates `java-jason/scenario-artifacts`; real runs create `java-jason/runtime-artifacts/*.jsonl`. These are expected outputs, not hidden background activity.

## What is and is not currently satisfied

| Expected capability | Current status |
|---|---|
| Fill pipeline and goal configuration | Yes |
| Deterministically generate workflow model | Yes |
| Deterministically generate BDI project beliefs/agent | Yes |
| Activate a local BDI agent | Yes; `RunLocalMAS` starts it in the foreground |
| Run real GitHub CI/CD from BDI | Implemented, but requires credentials, branch workflow, and reachable endpoints |
| Observe GitHub execution | Yes in GitHub Actions; summarized by the MAS adapter |
| Observe local telemetry | Yes through `/health` and `/metrics`; no built-in dashboard |
| Observe BDI decisions | Yes in the MAS console and structured JSON-lines logs |
| Inject deterministic execution errors | Yes through `BDI_EXECUTION_PLAN` and workflow inputs |
| Automatically compare expected vs actual mock behavior | Yes; Phase 3 has 8 passing scenarios |
| One-click three-window operator experience | Yes; `run-demo.ps1 -Mode real` |
| Live visual BDI/telemetry dashboard | No; not implemented in this prototype |

The framework and validation requirements are satisfied. The operator-experience expectation is only partially satisfied: the underlying BDI decision and telemetry records exist, but there is no one-command split-screen launcher or live dashboard yet.
